im2sim: AI-accelerated patient-specific simulation from medical images

An open-source Python library that builds hybrid image-graph neural networks to predict time-varying pressure and velocity fields from 3D medical images — turning hours of CFD into a 0.5-second inference. Built on PyTorch, PyTorch Geometric, VTK, and PyVista.

Stack: PyTorch · PyG · VTK · PyVista Inference: <0.5s (vs hours CFD) Use case: pulmonary artery hemodynamics License: open source
📚 Documentation 💻 GitHub 🔗 Image2Flow paper

Six concepts that make im2sim work

1. The 0.5-second prediction

The load-bearing claim of im2sim is not the architecture — it is the inference time. Traditional patient-specific CFD takes hours on HPC: mesh generation from segmentation, Navier-Stokes solve with patient-specific boundary conditions, post-processing. im2sim takes 0.5 seconds.

This is not an incremental speedup. It is a workflow phase change:

Traditional CFD workflow
Segment → mesh → solve → post-process. Hours to overnight. Iteration cycle: weekly.
im2sim inference workflow
MRI → trained network → field prediction. 0.5 seconds. Iteration cycle: during consultation.

Why this matters clinically

Surgeons plan interventions around the information they have during the consultation. A simulation that arrives overnight is consulted after the decision is already made. A simulation that arrives in 0.5 seconds becomes part of the decision loop — the surgeon can ask "what if we enlarge this stent?" and see the flow change before the patient leaves the room.

The 0.5s number is what separates a research demo from a clinical tool. Speed is not a convenience — it is the enabling property.

2. Hybrid image-graph architecture

im2sim does not use a pure CNN. It uses a hybrid image-graph network that processes the 3D MRI through one branch and the vessel-topology graph through another, fusing them before the final field prediction. This is the architecturally interesting decision, and it reflects a deep understanding of why vessels are hard.

Why pure CNNs struggle with vessels

Convolutional filters are translation-equivariant: a kernel that detects a vertical edge responds the same way regardless of where the edge appears in the image. This is perfect for tissue texture (lung parenchyma, myocardium) but wrong for vessels, because vessels are elongated, branching, and curving. A vessel that curves through the field of view does not respond consistently to a fixed kernel — the kernel sees "vessel cross-section" at some points and "vessel tangent" at others.

Why pure GNNs lose context

A graph neural network encodes "this vessel segment connects to that one" — the topology. But it discards the spatial context: where in the chest is this vessel? What tissue surrounds it? The graph alone cannot distinguish a pulmonary artery from a bronchus with identical topology.

Hybrid fusion (conceptual)

$$\mathbf{h}_{\text{fused}} = \text{Fuse}\!\left(\underbrace{\text{CNN}(\mathbf{X}_{\text{MRI}})}_{\text{anatomy + texture}},\ \underbrace{\text{GNN}(\mathcal{G}_{\text{vessels}})}_{\text{topology + connectivity}}\right)$$

Image branch + graph branch → fusion → field prediction
Left: 3D MRI volume processed by 3D CNN. Right: vessel graph processed by message-passing GNN. Center: fusion layer combines both representations. Output: pressure + velocity fields.

The image branch tells the network what the anatomy looks like; the graph branch tells it how the vessels connect. Neither alone is sufficient. This is the same architectural insight as FNO (clip 19): choose the representation that matches the structure of the problem.

3. The vessel tree as a graph

To build the graph branch, im2sim extracts the vessel tree from the MRI segmentation and represents it as a graph: nodes at branching points and segment endpoints, edges along vessel segments. Each node carries attributes (position, local radius, cross-sectional area); each edge carries attributes (length, average radius, orientation).

Graph definition

$$\mathcal{G} = (\mathcal{V}, \mathcal{E}), \quad \mathbf{v}_i = [\mathbf{x}_i, r_i, A_i], \quad \mathbf{e}_{ij} = [L_{ij}, \bar{r}_{ij}, \hat{\mathbf{n}}_{ij}]$$

Message passing on this graph propagates flow information along the vessel topology. A disturbance at the inlet (the main pulmonary artery) propagates through the graph to the distal branches — exactly as a pressure wave propagates in real hemodynamics. The GNN learns this propagation implicitly from data.

Vessel tree → graph extraction → message passing
A synthetic branching vessel tree (procedurally generated). Nodes (gold) mark branching points; edges (cyan) encode vessel segments. The GNN propagates information along edges.

Lazy generation note

The vessel tree above is generated procedurally in your browser using a recursive branching algorithm — no pre-computed dataset is shipped. Each render generates a fresh tree, so you can refresh to see different anatomies. For a real deployment with thousands of patient MRIs, the same lazy approach applies: generate the graph on-demand from the segmentation, not pre-store all graphs.

4. Time-varying pressure and velocity fields

The prediction is not a single static field. im2sim outputs time-varying pressure and velocity fields across the cardiac cycle — the pulsatile dynamics that determine wall shear stress, oscillatory shear index, and the hemodynamic indices clinicians actually use to assess disease risk.

Time-varying prediction

$$\hat{\mathbf{u}}(\mathbf{x}, t), \hat{p}(\mathbf{x}, t) = f_\theta\!\left(\mathbf{X}_{\text{MRI}}, \mathcal{G}_{\text{vessels}}\right), \quad t \in [0, T_{\text{cardiac}}]$$

Pressure field over cardiac cycle
Pulsatile pressure wave propagating from inlet to distal branches. Systole → diastole.
Velocity magnitude field
Peak systolic velocity. High velocity at stenoses, low in aneurysms.

The cardiac cycle is the natural temporal unit for hemodynamics. A network that predicts only a time-averaged field loses the pulsatile information that determines whether a region experiences laminar flow (healthy) or oscillating recirculation (atherogenic). Time resolution matters.

5. The digital twin vision

The long-term goal is a clinically useful digital twin: a patient-specific computational model that lives alongside the patient, updates with each scan, and supports clinical decisions throughout their care pathway. im2sim is the inference engine that makes this vision computationally tractable.

Digital twin loop: scan → model → predict → decide → rescan
Each clinical encounter updates the twin. The 0.5s inference enables multiple what-if scenarios per consultation.

What "clinically useful" actually requires

A digital twin is not just a fast simulation. It must be:

  • Validated against outcomes, not just against CFD ground truth
  • Uncertainty-aware — the surgeon needs confidence intervals, not point estimates
  • Generalizable across scanners and protocols — or explicitly scoped to one
  • Auditable — the prediction must be explainable to a clinician who did not build the network
  • Edge-case safe — congenital or post-surgical anatomy must trigger a flag, not a confident wrong answer

A digital twin is not a faster simulation. It is a model that earns clinical trust by being right, being clear about when it is unsure, and being safe when it is wrong.

6. Open science + extensibility

im2sim is explicitly designed as a flexible framework, not a cardiovascular-only tool. The library's modular design separates image processing, graph construction, network architecture, and simulation output — so the same scaffolding can serve other imaging modalities (CT, ultrasound) and other computational simulations (electrophysiology, structural mechanics, diffusion).

The stack

# im2sim dependency stack import torch # deep learning backend import torch_geometric as pyg # graph neural networks import vtk # 3D medical image processing import pyvista as pv # visualization + mesh handling # Hybrid image-graph network class HybridNet(torch.nn.Module): def __init__(self): self.image_branch = ImageEncoder(in_channels=1, hidden=64) self.graph_branch = GraphEncoder(node_features=6, edge_features=4) self.fusion = FusionLayer(image_dim=128, graph_dim=128) self.head = FieldPredictor(out_channels=4) # u, v, w, p def forward(self, image, graph): img_feat = self.image_branch(image) gph_feat = self.graph_branch(graph) fused = self.fusion(img_feat, gph_feat) return self.head(fused) # (B, 4, D, H, W, T)

By keeping the framework open and the dependencies standard, the team lowers the barrier for other labs to extend the approach to their own simulation targets — which is the right way to build a research ecosystem around an idea.

Analysis: risks, misdirection, and a better approach

im2sim is excellent engineering. The architecture is well-motivated, the inference speed is clinically transformative, and the open-source release is the right move for the field. But there are three places where the project (or anyone building on it) can be pulled off course. Here is what I would flag.

Risk 1: validating by MSE against CFD

The natural benchmark is "how close is the predicted field to the CFD ground truth?" But CFD itself is not ground truth — it is a simulation with its own assumptions: outlet boundary conditions are estimated, wall elasticity is approximated, blood is modeled as Newtonian. A network that matches CFD to 0.1% MSE has matched CFD's errors to 0.1%. The real validation metric is clinical decision change: did the AI prediction alter the surgical plan, and was the altered plan better for the patient? This requires prospective clinical studies, not retrospective MSE on a held-out test set. Without it, the 0.5s inference is a speedup of an unvalidated target.

Risk 2: physics violation without enforcement

If the network regresses velocity fields without a divergence-free constraint, it will produce predictions that look plausible but violate mass conservation. A velocity field with ∇·u ≠ 0 is physically impossible — but a CNN that minimizes MSE against CFD velocity fields has no incentive to enforce it. The result is a prediction that looks like blood flow but is not actually blood flow. This is exactly the PINN lesson (deep-dive §2): data fit does not imply physical correctness.

Fix: add a divergence-free penalty to the loss, evaluated at virtual collocation points inside the predicted field. The physics loss costs nothing at inference time (it is training-only) but structurally constrains the prediction.

Risk 3: domain shift across scanners

Train on Hospital A's 1.5T Siemens MRI protocol, deploy on Hospital B's 3T Philips — the image statistics differ, the vessel contrast differs, the artifact patterns differ. The 0.5s inference is meaningless if the network is confidently wrong on a different scanner. Multi-site training data with explicit cross-site validation is essential. Without it, the model works at the training hospital and fails silently elsewhere.

Better approach: four additions

  • Physics-informed loss — divergence-free constraint (∇·u = 0) as a soft penalty at collocation points, exactly like PINN L_phys. Training-only cost, structural correctness at inference.
  • FNO-style spectral layer for the field head — instead of pixel-wise 3D CNN output, use a Fourier spectral layer (clip 19). Mesh-independent, captures global flow structure, and supports zero-shot super-resolution: train on 64² voxels, evaluate on 256².
  • Ensemble or Bayesian uncertainty — the surgeon sees u(x,t) ± σ(x,t), not just a point estimate. Low-confidence regions (unusual anatomy, out-of-distribution) trigger a flag for traditional CFD verification.
  • Active learning loop — flagged low-confidence cases are queued for CFD verification. The CFD results are added back to the training set. The network improves on exactly the cases it currently fails — closing the loop between fast inference and slow verification.

The 0.5s number gets im2sim through the clinic door. Physics-informed loss, uncertainty, and active learning are what keep it in the clinic.
